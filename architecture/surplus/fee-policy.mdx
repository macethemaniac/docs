---
title: "Fee policy"
description: "How Lotus defines fee rules for price improvement and share improvement."
---

Fee policy defines how surplus and share improvement are split between users and the protocol.

The policy is versioned so a receipt can always explain which rules were active when an order executed.

## Fee types

Lotus captures fees on two distinct improvement types:

| Fee type | Source | Timing |
| --- | --- | --- |
| Price improvement fee | Better execution price versus the single-venue baseline | At execution time |
| Share improvement fee | Extra shares filled beyond what any single venue could supply | At execution time |
| Execution fee | Flat fee on filled notional | At execution time |
| Fast lane fee | Optional fee for prioritized execution | At execution time |

Price improvement and share improvement are independent — an order can produce one, both, or neither.

## Policy fields

A fee policy can include:

| Field | Meaning |
| --- | --- |
| `policyVersion` | Immutable version used on receipts. |
| `priceImprovementShareBps` | Lotus capture rate on price improvement, in bps. |
| `shareImprovementShareBps` | Lotus capture rate on share improvement value, in bps. |
| `executionFeeBps` | Flat fee on filled notional, in bps. |
| `maxTotalFeeBpsOfNotional` | Cap on total Lotus fees as a share of order notional. |
| `builderShareBps` | Share of price improvement paid to the integrating builder. |
| `maxBuilderFeeBpsOfNotional` | Cap on builder fee as a share of order notional. |
| `minimumUserSurplusBps` | Minimum improvement the user must retain after fees. |
| `eligibleRouteTypes` | Route types where the policy applies. |

## Price improvement fee formula

```text
priceImprovementFee = min(
  S_price * priceImprovementShareBps / 10000,
  N * maxTotalFeeBpsOfNotional / 10000
)
```

`S_price` is the USDC-normalized price improvement measured from verified fills.

## Share improvement fee formula

Share improvement is charged on the market value of extra shares obtained through multi-venue routing.

```text
extraShares = max(0, Q_exec - singleVenueMaxFillSize)
S_share = extraShares * P_exec
shareImprovementFee = S_share * shareImprovementShareBps / 10000
```

`singleVenueMaxFillSize` is committed at quote time. It represents the maximum fill available from the best single-venue alternative. Users receive the extra shares in full; Lotus captures only the configured share of their USDC value.

## Builder fee formula

```text
builderFee = min(
  S_price * builderShareBps / 10000,
  N * maxBuilderFeeBpsOfNotional / 10000
)
```

Builder fees apply to price improvement only, not share improvement.

## User-positive check

The user should keep positive improvement after fees:

```text
S_net_user = S_price - priceImprovementFee - builderFee
```

Required condition:

```text
S_net_user >= N * minimumUserSurplusBps / 10000
```

If this fails, the route should not advertise savings.

## Eligibility

Fee policy should apply only when:

- The order fills.
- Fill is confirmed and execution prices are verified.
- Realized improvement is positive.
- The route is eligible under the active policy.
- The user remains better off after fees.

Failed orders should not create surplus fees.

## Receipt requirements

Receipts should show:

- Policy version.
- Price improvement (gross and fee).
- Share improvement shares and fee, if any.
- Execution fee, if any.
- Builder fee, if any.
- Total Lotus fee.
- Fee cap applied, if any.

<Note>
  Fee policy is part of the execution contract. It is disclosed before the user places an order.
</Note>
