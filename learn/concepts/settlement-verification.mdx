title: "Settlement verification"
description: "Validate execution outcomes."
---

Settlement verification is how Lotus confirms that an execution actually produced the expected result.

Submitting an order is not enough. Lotus still needs to verify fills, venue status, settlement state, position accounting, and any recovery requirements.

## The execution lifecycle

![Lotus order flow](/images/learn/lotus-order-flow.svg)

An order can move through:

1. Previewed.
2. Placed.
3. Signed, if required.
4. Submitted.
5. Filled.
6. Verified.
7. Reflected in history, positions, and accounting.

## What Lotus verifies

Lotus checks:

- Submitted venue order IDs.
- Filled size.
- Fill price.
- Route leg status.
- Settlement status.
- User position updates.
- Venue balance or position snapshots.
- Whether any leg needs recovery.

## Why submitted is not final

A venue can accept an order before Lotus has confirmed the fill and accounted for the result.

The UI may show `SUBMITTED`, but final user accounting should wait for fill and settlement verification.

## Ghost-fill protection

A ghost fill is when a venue fill is real but the app fails to reflect it correctly.

Lotus tracks venue status and reconciles fills into trade history, settlement state, positions, and balances so the user's account view matches reality.

## User-facing result

The user should eventually see one clear result:

- Filled.
- Failed.
- Pending verification.
- Recovery required.

The detailed receipt remains available for audit.
