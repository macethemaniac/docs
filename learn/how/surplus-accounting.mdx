---
title: "Surplus accounting"
description: "How Lotus measures price improvement and share improvement and turns them into revenue."
---

Surplus is the extra value Lotus creates by executing better than a reference route.

Lotus recognizes two distinct types of improvement:

- **Price improvement** — a better average execution price per share than the best available single-venue route.
- **Share improvement** — more shares filled than any single venue could have supplied alone, by combining depth across venues.

Both types are transparent, disclosed at quote time, and measured from verified fills.

## The accounting flow

1. Build the reference route — the best safe single-venue route at preview time.
2. Record `singleVenueMaxFillSize` — the maximum shares the best single venue could fill.
3. Build candidate single, pair, tri, and RFQ-backed routes.
4. Score each route net of expected fees and slippage.
5. Select the best safe route.
6. Execute through the backend order flow.
7. Recalculate price improvement from verified fills.
8. Calculate share improvement from extra shares beyond `singleVenueMaxFillSize`.
9. Apply the active fee policy.
10. Write the receipt, user position, and revenue ledger entries.

Estimated surplus appears at preview time. Final surplus is calculated only after verified fills.

## Core terms

| Term | Meaning |
| --- | --- |
| `N` | User notional in USDC. |
| `Q` | Shares being bought or sold. |
| `P_ref` | Reference average price from the best safe single-venue baseline. |
| `P_exec` | Realized average execution price after route fills. |
| `singleVenueMaxFillSize` | Maximum shares the best single venue could fill at quote time. |
| `extraShares` | Shares filled beyond `singleVenueMaxFillSize` — only possible through multi-venue routing. |
| `S_price` | Gross price improvement, USDC-normalized. |
| `S_share` | USDC value of extra shares obtained through share improvement. |
| `F_protocol` | Lotus protocol fee. |
| `F_builder` | Builder fee, if configured. |
| `S_net_user` | Price improvement retained by the user after fees. |

For prediction markets, prices are quoted in USDC per share. A price of `0.24` means 24 cents per share.

## Price improvement

Price improvement captures better execution cost versus the single-venue baseline.

### Buy price improvement

For a buy, the user starts with USDC and wants as many shares as possible.

Reference shares:

```text
Q_ref = N / P_ref
```

Executed shares:

```text
Q_exec = sum(filled shares across all legs)
```

Price improvement (USDC-normalized):

```text
Delta_Q_price = max(0, Q_exec - Q_ref)
S_price = Delta_Q_price * P_exec
```

### Sell price improvement

For a sell, the user starts with shares and wants as much USDC as possible.

Reference proceeds:

```text
USDC_ref = Q * P_ref
```

Executed proceeds:

```text
USDC_exec = sum(leg proceeds after venue fills)
```

Gross price improvement:

```text
S_price = max(0, USDC_exec - USDC_ref)
```

## Share improvement

Share improvement captures extra fill capacity made available only by combining liquidity across multiple venues simultaneously.

```text
extraShares = max(0, Q_exec - singleVenueMaxFillSize)
```

The USDC value of those extra shares:

```text
S_share = extraShares * P_exec
```

A share improvement fee is charged at execution time:

```text
shareImprovementFee = S_share * shareImprovementShareBps / 10_000
```

The user receives all the extra shares. Lotus captures only a configured share of their USDC value. The default capture rate is 40%, meaning the user retains 60% of the extra value created by multi-venue routing.

<Note>
  `singleVenueMaxFillSize` is committed at quote time and signed alongside the route. It equals `0` when no single venue had any liquidity available for the order.
</Note>

## Fee policy

The active fee policy is versioned. A policy can define:

| Field | Purpose |
| --- | --- |
| `priceImprovementShareBps` | Lotus capture rate on price improvement. |
| `shareImprovementShareBps` | Lotus capture rate on share improvement value. |
| `executionFeeBps` | Flat fee on filled notional. |
| `maxTotalFeeBpsOfNotional` | Cap on total Lotus fees. |
| `builderShareBps` | Builder share of price improvement. |
| `minimumUserSurplusBps` | Minimum user-retained price improvement. |

Price improvement fee (capped):

```text
priceImprovementFee = min(
  S_price * priceImprovementShareBps / 10000,
  N * maxTotalFeeBpsOfNotional / 10000
)
```

Builder fee:

```text
builderFee = min(
  S_price * builderShareBps / 10000,
  N * maxBuilderFeeBpsOfNotional / 10000
)
```

User-retained price improvement:

```text
S_net_user = max(0, S_price - priceImprovementFee - builderFee)
```

The route remains user-positive when:

```text
S_net_user >= N * minimumUserSurplusBps / 10000
```

If this condition fails, Lotus should choose a different route or show no savings.

## Example — price improvement

A user buys `100 USDC` of a Yes outcome.

The best safe single venue averages `0.2500`.

```text
Q_ref = 100 / 0.2500 = 400 shares
```

Lotus routes a pair route. Verified average price: `0.2420`.

```text
Q_exec = 100 / 0.2420 ≈ 413.2 shares
singleVenueMaxFillSize = 413.2 (single venue could fill the whole order — no share improvement)
Delta_Q_price = 413.2 - 400 = 13.2 shares
S_price = 13.2 * 0.2420 ≈ 3.19 USDC
```

If the protocol captures `20%` of price improvement:

```text
priceImprovementFee = 3.19 * 0.20 ≈ 0.64 USDC
S_net_user = 3.19 - 0.64 ≈ 2.55 USDC
```

## Example — share improvement

A user buys `100 USDC` of a Yes outcome on a low-liquidity market.

The best single venue can only fill `300 USDC` worth of shares. No single venue has more depth.

```text
singleVenueMaxFillSize = 300 shares  (committed at quote time)
```

Lotus routes a cross-venue order. Verified fills across two venues: `420 shares` at average price `0.2381`.

```text
Q_exec = 420 shares
extraShares = max(0, 420 - 300) = 120 shares
S_share = 120 * 0.2381 ≈ 28.57 USDC
shareImprovementFee = 28.57 * 0.40 ≈ 11.43 USDC
```

The user receives all 420 shares. Lotus earns 11.43 USDC on the extra 120 shares unlocked by multi-venue routing. Without multi-venue routing, the user could not have filled those shares at all.

## What the receipt should include

The final receipt should include:

- Reference route and `P_ref`.
- `singleVenueMaxFillSize`.
- Executed route and `P_exec`.
- Filled size per leg.
- Price improvement (gross and fee).
- Share improvement (extra shares and fee), if any.
- Execution fee.
- Builder fee, if any.
- User-retained price improvement.
- Fee policy version.
- Settlement verification result.

<Note>
  Surplus accounting is measured from verified fills. Preview math is an estimate.
</Note>
