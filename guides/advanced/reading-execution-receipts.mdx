---
title: "Reading execution receipts"
description: "How to understand the final record of a Lotus trade."
---

An execution receipt is the audit record for a completed or failed order.

It should explain what the user approved, what Lotus submitted, what the venue returned, and how settlement was verified.

![Lotus order flow](/images/learn/lotus-order-flow.svg)

## What a receipt should show

A receipt can include:

- Order ID.
- Quote ID.
- Execution ID.
- User-facing state.
- Route type.
- Venue legs.
- Signed payload reference.
- Submitted venue order IDs.
- Fill size and price.
- Fees and surplus.
- Settlement verification result.
- Any fallback route used.
- Any final error.

The receipt should be enough to reconstruct the execution outcome.

## Reading per-leg fills

For every route leg, check:

- Venue.
- Expected size.
- Filled size.
- Expected price.
- Actual fill price.
- Venue order status.
- Settlement status.

For pair and tri routes, the final result depends on all legs.

## Reading failure receipts

A failed receipt should explain the safety gate that stopped execution.

Examples include:

- Quote expired.
- Price moved outside tolerance.
- Funding readiness blocked.
- Sell position not verified.
- Venue token ID missing.
- Submit path not configured.

The message should be clear, but production users should not see raw provider secrets or internal stack traces.

## Common mistakes

- Do not treat `SUBMITTED` as final if fill verification is still pending.
- Do not hide fallback behavior from the receipt.
- Do not drop per-leg errors from multi-venue routes.
- Do not expose signed payloads or secrets in receipts.

<Warning>
  Receipts are part of the trust surface. They must be complete, but sanitized.
</Warning>
