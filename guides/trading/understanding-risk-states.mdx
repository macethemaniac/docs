Risk states explain whether a route can be executed safely.

They help users understand the next action without reading backend diagnostics.

![Display versus execution](/images/learn/display-vs-execution.svg)

## User-facing states

The normal trading UI should stay simple:

- **Place order** when the route is ready.
- **Sign** when a venue requires approval.
- **Enable venue** when setup is required.
- **Filled** when the order completes.
- A clear failure message when user action is needed.

The user-facing interface should not show technical labels, cache misses, or low-level readiness codes.

## Detailed route states

Lotus can track detailed route states to explain why an order can or cannot proceed.

Examples include:

- Fresh quote available.
- Quote expired.
- Venue setup missing.
- Funding not ready.
- Sell token ID missing.
- Venue orderbook moved.
- Settlement verification pending.

These details are most useful in receipts, advanced route views, and troubleshooting flows.

## Why Lotus simplifies route labels

Technical route labels are often implementation details.

For example, a user does not need to know whether a quote snapshot cache missed. They need to know whether the order can be placed now, whether they must enable a venue, or whether Lotus is still updating prices.

## Common mistakes

- Do not show `partial`, `stale`, or `cache miss` on production cards.
- Do not label a route as executable when a safety gate failed.
- Do not turn backend diagnostics into user-facing copy.
- Do not hide actionable setup requirements.

<Warning>
  Display can be smooth, but execution must stay strict.
</Warning>
