---
title: "Understanding fallbacks"
description: "When Lotus can recover a route and when it must fail closed."
---

A fallback is a pre-approved recovery path for an order.

Lotus can use a fallback only when it is inside the authorized execution scope and still passes live execution checks.

## When fallback routes help

Fallbacks can help when:

- A venue rejects an order because the book moved.
- A route leg is no longer fresh.
- A simpler route is still executable.
- A multi-leg route can be safely reduced.

For example, a tri route may fall back to a pair route if the third leg becomes unsafe before submit.

## When Lotus should fail closed

Lotus should not improvise a new route after the user approved a different one.

Lotus should fail closed when:

- The fallback was not authorized.
- The market or outcome changed.
- The venue set changed outside scope.
- Slippage tolerance would be exceeded.
- Funding readiness is missing.
- A sell route cannot verify the position.
- Settlement would become ambiguous.

## What users should see

Users should see a simple result:

- The order filled through the selected route.
- The order filled through an allowed fallback.
- The order failed because no safe fallback existed.

The receipt should show the route actually used.

## Common mistakes

- Do not call any retry a fallback. A fallback must be pre-scoped.
- Do not use stale display data to recover execution.
- Do not hide a fallback fill from the final receipt.
- Do not route to a different venue preference when the user selected a specific venue.

<Warning>
  Fallbacks are safety paths, not permission to smart-route around user authorization.
</Warning>
