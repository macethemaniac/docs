---
title: "Architecture decisions"
description: "Security-driven decisions in the Lotus architecture."
---

Lotus uses a few core architecture decisions to keep execution safe.

This page explains the decisions users and builders should understand.

## Backend-owned execution

The backend owns order orchestration.

Reason: the frontend should not decide when a route is safe to submit. The backend can revalidate quote freshness, funding readiness, signatures, idempotency, and settlement support.

## Separate display from execution

Lotus separates live display data from executable quote authority.

Reason: market cards and charts should feel fast, but trades must require fresh execution gates.

## Fail closed by default

Lotus refuses execution when safety cannot be proven.

Reason: forced execution through stale or incomplete data can create bad fills, settlement mismatches, or unrecoverable positions.

## Use scoped authorization

Execution scope tokens bind authority to a route, side, size, price band, venue set, and expiry.

Reason: user approval should not become broad backend discretion.

## Verify after submit

Settlement verification is separate from venue submit.

Reason: the app should not treat a venue acknowledgement as final position accounting.

## Reader takeaway

Lotus keeps the user flow simple by moving safety-critical work into backend systems that can revalidate, submit, verify, and reconcile execution.
